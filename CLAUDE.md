# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Never ever use agents and sub agents to keep all context inline.

## Commands

```bash
pnpm dev           # dev server on :3000
pnpm build         # production build
pnpm typecheck     # tsc --noEmit
pnpm test          # vitest (unit, jsdom)
pnpm test:watch    # vitest watch mode
pnpm test:e2e      # playwright E2E
pnpm smoke:git     # native git CLI vs the real /api/git route (in-memory DB + fake S3; isolated git config)
pnpm test:coverage # vitest with coverage report
pnpm check         # biome lint + format check
pnpm lint          # biome lint only
pnpm format        # biome format (write)
pnpm db:push       # push schema to Neon (no migration files)
pnpm db:generate   # generate drizzle migration files
pnpm db:migrate    # run generated migrations
pnpm db:studio     # drizzle studio UI
pnpm deploy        # build (deployment target is Vercel via the nitro "vercel" preset, not Cloudflare — R2 is used only for storage)
```

Run a single test file: `pnpm test src/server/__tests__/repo-access.test.ts`

**pnpm install quirk**: `pnpm-workspace.yaml` must have `packages: ['.']` or `pnpm add` / `pnpm install` will fail with "packages field missing or empty". To add a dependency, edit `package.json` directly then run `echo "Y" | pnpm install`.

**Don't trust the pnpm deprecation warning about `package.json`'s `"pnpm"` field.** On the pinned `packageManager` version (see `package.json`), `pnpm install` prints `The "pnpm" field in package.json is no longer read by pnpm... See pnpm.io/settings for the new home`, but that's wrong for this version: `pnpm-workspace.yaml`'s `overrides` key has no effect here, while `package.json`'s `"pnpm": { "overrides": {...} }` (used for the CVE-cap pins — see `docs/security.md`) still works correctly, warning aside. Verified empirically (overriding a throwaway top-level dep and checking `pnpm ls`) after moving it once and accidentally reintroducing 14 high-severity transitive vulnerabilities that a fresh `pnpm audit` had to catch. If a future pnpm/Node upgrade repeats this warning, re-verify before acting on it — don't just move the config.

**After schema changes**: run `pnpm db:push` (dev/fast) or `pnpm db:generate && pnpm db:migrate` (migration files) to apply to Neon.

## Architecture

**Framework**: TanStack Start (file-based SSR router, server functions via `createServerFn`).

**Routing**: `src/routes/` — file-based. API routes live under `src/routes/api/`. The catch-all git route is `src/routes/api/git.$.ts` (handles the full Git HTTP smart protocol).

**Server logic**: `src/server/` — pure server-side modules, imported only inside `createServerFn` or API handlers. Key modules:
- `git-fs.ts` — the R2-backed isomorphic-git `fs`, composed from the published `git-fs-s3` package (which was extracted from this app's former inline `git-r2-backend.ts`; the deep fs/cache behavior now lives — and is tested — in that package). Every git read **and write** goes through it — there is no local disk anywhere. Stack, network-outward: the R2 store (`src/lib/r2.ts`; without R2 env, a `MemoryObjectStore` — production throws instead) → retry/circuit-breaker (`createRetryStore`, with a fetch-aware `isRetryable`) → `perfR2` instrumentation → LRU cache (request coalescing, negative + dir-listing caching, `invalidate(prefix)`) → git-aware fs (loose-object hints, registered gitdirs). Gitdirs are the full storage roots, so fs paths map 1:1 onto R2 keys. `registerRepoGitdir(owner, repo)` registers a repo's gitdir with the fs (`getBareRepoOptions` and the git HTTP handlers call it) so isomorphic-git's per-command gitdir `stat` and its `packed-refs`/`shallow` probes cost zero R2 calls; only call it once the repo's DB row is known to exist. `refAwareTtl`/the S3 content type classify keys with `git-storage-naming.ts`'s `parseRepoGitStorageKey` plus `git-fs-s3`'s typed `classifyGitdirPath` — don't pattern-match key strings. Every isomorphic-git call must carry the shared per-repo `cache` (`getRepoCache`, via `getBareRepoOptions`): without it each object read re-parses every pack index. Exports call-site wrappers `detectLooseObjectsHint(owner, repo)` / `prefetchAllPacks(owner, repo)` (call the former before any new full-history walk — both `getCommitLog`'s walk and `handleUploadPackIso`'s clone/fetch-serving walk already do), the prefix-level storage operations `listRepoStorage`/`getRepoStorageSize`/`deleteRepoStorage`/`moveRepoStorage` (uncached, R2 server-side copy for moves) plus `putStorageObject` for operator scripts, and the invalidation hooks `invalidateRepoGitStorage(owner, repo)` / `invalidateGitStorageKeys(keys)` — writes *through* `gitFs` keep the cache current on their own, but **anything that writes to a repo's R2 prefix around this fs must call these** (the prefix operations here already do) or warm instances serve stale reads. It owns the app's single R2 store instance — don't construct another.
- `git-storage-naming.ts` — canonical R2 key derivation (`repos/{ownerKey}/{repoName}/git/…`); owns all storage key construction — never construct R2 keys manually
- `git-http-iso.ts` — thin pushstack-specific wrapper around `git-fs-s3`'s `/http` smart-HTTP module (the pkt-line framing, reachability walk, receive-pack ref-CAS logic, and pack consolidation live there now — this file used to hand-roll all of it; `/http` was extracted from an earlier version of this exact file, the same way `git-fs.ts` was extracted from the old `git-r2-backend.ts`). What stays here: auth checks (`GitAuthorizationError` on missing read/write access), running `handleReceivePackIso`/`repackRepositoryNow` against `gitFs` under `withRepositoryLock` followed by `afterRepositoryPush` (all services run straight on R2 — the pack, its index, ref CAS and the repack's stale-pack deletes are all `gitFs` writes), and wiring `perfStep`/`logWarn` into the library's `HttpHooks`. Request bodies go through `readGitRequestBody`, which enforces `GIT_HTTP_MAX_BODY_BYTES` while streaming (a chunked body declares no length, and upload-pack is anonymous on public repos). `receivePackResponse` gets the request's parsed `capabilities` (side-band-64k framing, report-status) and `unpackError`. `repackIfNeededUnlocked(ownerKey, repoName)` is the threshold-gated repack for non-push writes — `git-commit-write.ts`/`git-merge-iso.ts` call it inside their lock, since every web commit/merge now adds one pack (`git-fs-s3` 0.8's packed writes; nothing in the app writes loose objects, which is what keeps the cross-process loose-object hint correct — wrap any new object-writing code in `withPackedWrites`). Every client-supplied ref-update `refName` is validated by the library's own `applyRefUpdates` (`isSafeFullRefName`, same regex as `git-ref-name.ts`'s — see the dedup note there) before it ever reaches `git.resolveRef`/`deleteRef`/`writeRef`, unconditionally, not as something this file has to remember to call.
- `git-ref-name.ts` — re-exports the branch/ref-name/path validators (`isSafeBranchName` for bare names, `isSafeFullRefName` for `refs/heads/…`/`refs/tags/…`, mirroring isomorphic-git's own internal `isValidRef` character-class rules) from `git-fs-s3`'s `refs.ts` — extracted from an earlier version of this exact file, so the checks stay in one place instead of two copies drifting apart — and layers this app's zod schemas on top (`safeBranchNameSchema`, `safeRefNameSchema`, `safeCommitShaSchema`, `safeRepoPathSchema`). Used by `git-http-iso.ts`/`git-repo-storage.ts` above, by every branch-name-shaped zod field in `files.ts`/`pull-requests.ts`, and as a defense-in-depth guard inside `git-branch-ops.ts`/`git-commit-write.ts`/`git-merge-iso.ts` immediately before their isomorphic-git calls — `git.commit`/`git.merge`/`git.deleteBranch` have the same no-internal-validation gap as the receive-pack primitives above, and are reachable from ordinary web-UI actions (branch delete, PR merge), not just a raw git push. `isSafeRefName`/`safeRefNameSchema` (branch name OR full 40-hex commit SHA — `isSafeBranchName` alone deliberately rejects SHA-shaped values) covers the read-path `branchName` fields in `files.ts` that the blob page's SHA-pinned Permalink view relies on; `isSafeRepoPath`/`safeRepoPathSchema` (relative, no `..`, no `.git/` prefix, no null bytes) is shared by `files.ts` and `api/raw.$.ts` — the latter reads path/ref segments straight off the URL rather than through a validated `createServerFn`, so it validates both explicitly before they reach `getFileContent`.
- `git-auth.ts` — per-request git auth; fallback chain: Better Auth session → PAT (password starting with `ghp_`) → username/password. The password-auth path is rate-limited (10 failed attempts / 5 min per username/email) via a `git_auth_attempts` DB table — not an in-process `Map`, since the git HTTP endpoint runs across multiple concurrent/cold-starting Vercel instances that don't share process memory.
- `git-cache.ts` — in-process LRU parsed-object cache (`getCachedObject`/`setCachedObject`) storing JS values directly to avoid JSON.parse overhead on hot paths; backs every `ops.*` result cache below. (The raw git-object Buffer cache that used to live here moved into `git-fs-s3`'s `createCachedStore`, composed in `git-fs.ts`.) Also exports `resultCache` — `{ get: getCachedObject, set: setCachedObject }` typed as `git-fs-s3/ops`'s `ResultCache` — the one shared instance every ops-delegating file below passes as `hooks.resultCache`, so they aren't each re-declaring the same adapter.
- `git-tree-ops.ts`, `git-branch-ops.ts`, `git-commit-write.ts`, `git-diff-iso.ts`, `git-history-ops.ts`, `git-last-commit.ts`, `git-file-history.ts` — thin wrappers around `git-fs-s3/ops` (extracted from earlier versions of these exact files — `git-tree-ops.ts` is a pure re-export, since its functions already take a resolved `Repo` with no app-specific glue needed). What stays in each: resolving `(ownerKey, repoName)` to a `Repo` via `getRepoOptions`/`getBareRepoOptions` (`git-repo-storage.ts`/`git-manager-iso.ts`), the per-repo lock around writes (`createBranch`/`deleteBranch`/`setDefaultBranch` in `git-branch-ops.ts`, `createCommit`/`deleteFile` in `git-commit-write.ts` — straight to R2 via `commitFilesToBare`/`deleteFileFromBare`, no worktree — both validate `branch`/`branchName` with `isSafeBranchName` first; a commit must target an existing branch, or be the first commit of an empty repository — new branches come only from `createBranch`; `setDefaultBranch` in `git-branch-ops.ts` points git's `HEAD` at a branch and `updateRepository` keeps `repositories.defaultBranch` in step), and wiring `git-cache.ts`'s `resultCache` + `perf-log.ts`'s `perfStep`/`perfNote` + `git-fs.ts`'s `prefetchAllPacks` into the library's `OpsHooks` via `git-cache.ts`'s shared `opsHooksFor(ownerKey, repoName, options?)` — used to be rebuilt by hand, near-identically, in each of `git-history-ops.ts`/`git-last-commit.ts`/`git-file-history.ts`; `git-history-ops.ts` is the one caller that passes `{ prefetchMinDepth: 1 }` (see `PREFETCH_PACKS_MIN_DEPTH` there). The library implements the exact result-cache-keyed-by-head-sha pattern (`getCommitLog`, `getTreeFromRef`, `getCommitHistory`, `getLastCommitsForTree`, `getFileHistory`) these files used to hand-roll — don't bypass it by calling `git.log`/`git.readTree` directly. Cache keys are namespaced `` `<kind>:${gitdir}:...` `` by the library itself (`resultKeyPrefixes(gitdir)`, used by `git-repo-storage.ts`'s post-sync invalidation — see below); they are **not** app-namespaced by `ownerKey`/`repoName` the way this app's other caches are. `git-last-commit.ts`'s two-phase prefetch-then-resolve walk (fixed-size batches, `PREFETCH_WINDOW`) and `git-history-ops.ts`'s pack-prefetch gating (`PREFETCH_PACKS_MIN_DEPTH`) both live in the library now too; deep test coverage for the walk algorithms themselves is in `git-fs-s3`'s own `test/ops.test.ts`/`test/ops-tree.test.ts`, not duplicated here — this app's tests (`git-integration.test.ts` plus each file's own, where one still exists) cover the wrapper wiring and app-specific orchestration, using real repos rather than mocking isomorphic-git (that package resolves its own isomorphic-git copy under pnpm's isolated node_modules layout, so a mock declared here never reaches its internal calls).
- `git-merge-iso.ts` — `analyzeMerge` delegates to `git-fs-s3/ops`'s `analyzeMerge`. `mergeBranches` runs the fast-forward check (`git-fs-s3/ops`'s `fastForwardMerge`) and, when it doesn't apply, a real non-fast-forward merge via `git-edge`'s `threeWayMerge` — both inside one `withRepositoryLock` span, so a concurrent write can't land between the FF check and the merge and make it stale. `threeWayMerge` works directly on the object graph (trees, blobs, commits) with no worktree, unlike isomorphic-git's own `git.merge` — a bare repo living entirely in R2 has no disk to check one out onto. Both validate `sourceBranch`/`targetBranch` with `isSafeBranchName` before any git call. `mergeBranches` catches `git-edge`'s `GitMergeConflictError` (`.conflictingPaths`) and reports it as a structured conflict; any other error propagates.
- `git-repo-lock.ts` — per-repo locking (`withRepositoryLock`, backed by a Postgres lease row — `repo_locks` — not an in-process mutex, since Vercel serverless instances share no memory across invocations; see `docs/git-storage.md`); every write (push, repack, commit, branch/HEAD change, merge, rename, create, delete) runs inside it. The 60s lease is renewed every 20s while the holder runs (a long push/repack keeps it); a killed holder stops renewing and its lease clears within one TTL. `withRepositoryLock` is **not reentrant** — a locked function must never call another locked function for the same repo, or it deadlocks (now: times out and throws after ~65s rather than hanging). It also records a best-effort WAL entry per critical section via `git-transactions.ts` (the `git_transactions` table). `git-repo-storage.ts` re-exports it.
- `git-repo-storage.ts` — what's left of storage orchestration now that every read and write goes straight through `gitFs` (no hydrate, no sync-back, no worktree): `getRepoOptions` (= `getBareRepoOptions`), post-push bookkeeping, and rename/delete of a repo's whole prefix. Exports `qualifyBranchRef(ref)` — re-exported from `git-fs-s3` (extracted from an earlier version of this exact function) — qualifies a bare branch name to `refs/heads/<name>` before handing it to isomorphic-git, since resolving a bare name makes it try several guaranteed-to-fail candidate paths first; use it at any new call site that resolves a branch by name (this app's ref model is branch-only, never tags). `afterRepositoryPush(ownerKey, repoName, ownerDbId?)` (called inside the lock after a push/repack) invalidates every `ops.*` result-cache entry via `resultKeyPrefixes(getRepoGitStorageRoot(ownerKey, repoName))` (from `git-fs-s3/ops`) — **must** use that exact `gitdir` value (what `getRepoOptions` resolves), not a hand-rolled `${ownerKey}/${repoName}` prefix; the two don't match, and there was a real bug here where they didn't (see `git-repo-storage.test.ts`'s regression test) — drops the per-repo isomorphic-git cache (a repack replaces packs), and records `repositories.diskUsage` from one listing without delaying the response. Nothing here creates a repository: storage comes only from `createRepository`'s `initBareRepo`. `renameRepositoryStorage(ownerKey, oldName, newName)` moves a repo's storage (R2 server-side copy, old keys deleted only after every copy succeeds) when its DB row is renamed — every storage key here is name-derived, so a rename that only touched the DB row used to silently orphan the old commit history under the old prefix. Doesn't lock internally; callers must wrap both the move and the DB update in one `withRepositoryLock` call (see `repositories.ts`'s `updateRepository`). `deleteRepositoryStorage` likewise. `createRepository` inserts the row first (the unique index is the real guard), then under the lock clears any orphaned storage under the name and inits — rolling the row back if init fails; `deleteRepository` deletes the row first, then the storage (a failed cleanup only leaves unreachable objects, which the next create of that name clears).
- `repo-access.ts` — the single place computing `RepositoryAccess`; also exports `getRepoOrThrow(repoId)` / `requireReadAccess(repoId, userId)` / `requireWriteAccess(repoId, userId)` request helpers — use these instead of hand-rolling a repo-fetch-then-check block in a new handler. `readWithAccess(label, repoId, fn)` is the higher-level helper for read-side `createServerFn` handlers specifically: it's the `perfContext` → `getCurrentUserOptional` → `getRepoWithReadAccess` → `fn(repo)` shape that used to be copy-pasted at nearly every read handler in `files.ts`/`issues.ts`/`pull-requests.ts` — `fn` gets the already-access-checked repo for handlers that need its storage coordinates; handlers that only need the access gate can ignore the param. `requireOwner(repoId, userId, message)` is the equivalent for the "fetch the repo, throw `message` unless the caller is its owner" shape repeated across `repositories.ts`'s owner-only actions (rename, delete, repack, manage collaborators). Note these are broader-than-owner checks (any write collaborator passes `requireWriteAccess`); owner-only actions still need `requireOwner`/an explicit `repo.ownerId !== user.id` check, not just `requireWriteAccess`. If a handler already fetched the repository row via a relation (e.g. `db.query.issues.findFirst({ with: { repository: true } })`), call `getAccessForRepository(repo, userId)` instead of `canReadRepo(repoId, userId)` — the latter re-fetches the repo row from scratch. Its own short-TTL access cache, and `repositories.ts`'s separate repo-row-by-name cache, both go through `ttl-cache.ts`'s `createTtlCoalescedCache` (TTL + in-flight coalescing) instead of each hand-rolling the same two-Map shape.
- `issues.ts`, `pull-requests.ts`, `comments.ts` — split by resource (formerly one `issues.ts`); each owns its own schema validation, access checks, and activity logging for that resource. Issues and PRs share one repo-scoped number sequence (`issues.number`/`pullRequests.number`, GitHub's numbering model) instead of exposing their own DB `id` — `createIssue`/`createPullRequest` claim the next number via `repositories.ts`'s `claimNextIssueOrPrNumber`, and `getIssueByNumber`/`getPullRequestByNumber` resolve the `$id` route param (which is this `number`, not the internal `id`) by `(owner, name, number)` server-side, so route loaders don't need to sequence behind a separate repo fetch. `getIssueNumbers`/`getPullRequestNumbers` return this `number` list too — the disambiguation source for `MarkdownRenderer`'s `#123` reference autolinking (`reference-patterns.ts`/`remark-autolink-references.ts`). `pull-requests.ts`'s `mergePullRequest` matches a merged PR body's `getClosingIssueNumbers` ("Closes #4" etc.) against `issues.number` (scoped by `repoId`), not `id`. Comment/issue/PR activity `metadata.issueId`/`metadata.prId` (consumed by `src/lib/activity.ts` as route-param values, not real FKs) store this same `number` — `comments.ts`'s `createComment` looks it up off the issue/PR row it already fetched for validation.
- `git-manager-iso.ts` — foundation layer: `getBareRepoOptions` (always `gitFs`, the registered gitdir, and the shared per-repo isomorphic-git cache), `initBareRepo`, `invalidateRepoGitCache`.
- `git-errors.ts` — re-exports `GitError` and its shared subclasses (`GitPathNotFoundError`, `GitObjectNotFoundError`, `GitConflictError`, etc.) plus `formatErrorResponse` from `git-fs-s3` (extracted from an earlier version of this exact file) — this has to be the same class hierarchy the library's `ops`/`http` functions throw internally (e.g. `getFileContent`'s `GitPathNotFoundError`), or `formatErrorResponse`'s `instanceof GitError` checks silently miss library-thrown errors and fall through to an opaque 500. Also exports `isGitNotFoundError` (missing repo/ref/path/object → 404 on read paths).
- `files.ts` — server functions for file/branch/commit operations exposed to routes. `getFile` returns a `FileView` (`src/lib/file-view.ts`): inline `content` only for text up to `MAX_INLINE_TEXT_BYTES`; binary and larger files come back as `{ kind, size }` and the UI fetches their bytes from `/api/raw` (`rawFileUrl`) only when previewing or downloading. Diffs (`git-fs-s3`'s `DiffFile.kind`) likewise never carry file content; `FileDiffViewer`'s `sides` gives the refs to preview binary sides from `/api/raw`. `/api/raw` streams its body (a non-streamed function response is capped at 4.5 MB on Vercel). (create/edit/delete file, branch create/delete), composing `git-commit-write.ts`, `git-branch-ops.ts`, and `git-diff-iso.ts`. Read-path `branchName` fields (`getFile`/`listFiles`/`getLastCommits`/`getFileHistory`/`getCommits`) use `safeRefNameSchema` (branch name or full commit SHA), not `safeBranchNameSchema` — the blob page's Permalink view passes a commit SHA in that field, which `safeBranchNameSchema` alone would reject. Write-path branch fields (`uploadFile`/`deleteFile`/`createBranch`/`deleteBranch`/`getBranchDiff`) keep the stricter SHA-rejecting schema, since a SHA is never a meaningful branch name there. `getCommit`/`getCommitDiff`'s `commitSha` field uses `safeCommitShaSchema`.
- `repositories.ts` — repo CRUD, stars, and collaborator-facing server functions; delegates access checks to `repo-access.ts` and storage deletion to `git-repo-storage.ts`. `updateRepository` checks for a name collision and, on an actual rename, wraps `renameRepositoryStorage` + the DB update in one `withRepositoryLock` call — see `git-repo-lock.ts` above. Also exports `findRepositoryByName(ownerUsername, repoName)` — a plain function (not a `createServerFn`), so other server modules (`issues.ts`/`pull-requests.ts`'s `getIssueByNumber`/`getPullRequestByNumber`) can resolve a repo by owner/name inline without a network round trip; shares `fetchRepoRowByName`'s cache with `getRepositoryByName` and the git HTTP protocol's own repo resolution. `claimNextIssueOrPrNumber(repoId)` atomically increments and returns the pre-increment value of `repositories.nextIssueNumber` — the shared issue/PR number sequence's single source of truth (see `app-schema.ts`'s `nextIssueNumber` doc comment and `docs/database.md`).
- `search.ts` — cross-entity search (repos, issues, users) and activity feeds, gated per-result by `canReadRepo`. Follows the same "public + anonymous = read" model as everywhere else: `searchRepositories`/`searchUsers`/`getGlobalActivity`/`getRepositoryActivity`/`searchIssues` use `getCurrentUserOptional()`, not `getCurrentUser()` — none of them return anything an anonymous visitor couldn't already reach via a direct public-repo URL, so they shouldn't hard-require login. `getUserActivity` follows the same model when an explicit `userId` is given (non-self viewers only see public-repo activity); it only throws for an anonymous caller with no `userId`, since that case defaults to "my own" activity. Any activity query whose results feed `describeActivity` (`src/lib/activity.ts`) must fetch `repository: { with: { owner: true } }` — a bare `repository: true` leaves `owner` undefined and every activity link silently points at `/repo/unknown/…`.
- `tokens.ts` — personal access tokens for git over HTTPS (`listTokens`/`createToken`/`revokeToken`, Settings → Git access). A token is `TOKEN_PREFIX` + random bytes, shown once; only its SHA-256 (`hashToken` — async, WebCrypto — shared with `git-auth.ts`) is stored. Scopes are the typed `TokenScope` (`src/lib/token-scopes.ts`): `repo:read` | `repo:write`, write implies read, at least one required.
- `users.ts` — `getUserProfile(username)`: public profile data (user's public fields + visible repositories + recent activity, one round trip, anonymous-readable — self sees private repos/activity too); powers the `/users/$username` profile page, which search results and `RepoHeader`'s owner link navigate to.
- `perf-log.ts` — request-scoped timing instrumentation for diagnosing slow page loads. `perfContext(label, fn)` wraps a `createServerFn` handler (AsyncLocalStorage-based, so nested calls don't need the context threaded through every function signature); `perfStep(label, fn)` times an awaited sub-call, and anything it starts nests one level deeper; `perfR2(label, fn)` also tallies R2 calls; `perfNote(text)` adds a note (every SQL statement's text arrives this way, from `db/index.ts`). Each request prints as one indented tree when it ends. All of it is a no-op unless `isPerfLogEnabled()` (`src/lib/perf-log.ts`): always in dev, on the server with `PUSHSTACK_PERF_LOG=1`, in a browser when `localStorage["pushstack:perf-log"] === "1"` (Settings → Developer). `src/lib/perf-log.ts`'s `perfTime`/`perfMark` are the client/SSR counterparts used in route loaders and `query-options.ts` queryFns (`[perf:ssr]`/`[perf:client]`). Follow this pattern (wrap the handler in `perfContext`, each meaningfully-awaited sub-call in `perfStep`) for new server functions on a user-facing read path. `logError(scope, message, err)`/`logWarn(scope, message, err?)` always log: `logError` also forwards to `Sentry.captureException`, `logWarn` adds a Sentry breadcrumb. Use them instead of a bare `console.error`/`console.warn` in server code.

## Error tracking (Sentry)

Wired via `@sentry/tanstackstart-react`, gated entirely on `VITE_SENTRY_DSN` being set (the SDK no-ops without a DSN, so it's safe to leave unset in dev). Four integration points, each covering a different class of error TanStack Start doesn't route through a single shared boundary:

- `instrument.server.mjs` (repo root) + `src/server.ts` (`wrapFetchWithSentry` around the default fetch handler) — server-side init and the HTTP-level catch-all. Vercel functions can't use Node's `--import`/`NODE_OPTIONS` preload flag the way a long-running server could, so this explicit-import-plus-wrap pattern is the supported alternative for this deploy target (see `docs/deployment.md`).
- `src/start.ts` (`createStart` with `sentryGlobalRequestMiddleware`/`sentryGlobalFunctionMiddleware` first in their arrays) — catches thrown errors from every request and every server function.
- `src/router.tsx` (`Sentry.init` inside `if (!router.isServer)`) — client-side init, mirrors the server init with the same DSN.
- `src/routes/__root.tsx`'s `RootErrorComponent` (`useEffect` calling `Sentry.captureException(error)`) — the one gap the middleware above doesn't cover: exceptions raised during route *rendering* (SSR or client), not from a server function or request handler. Any new top-level error boundary added elsewhere should do the same.

`vite.config.ts` conditionally adds the `sentryTanstackStart` vite plugin (source map upload) only when `SENTRY_AUTH_TOKEN` is set, so local/CI builds without one are unaffected.

**Storage**: All git data lives in Cloudflare R2. The virtual filesystem root for a repo is `repos/{ownerKey}/{repoName}/git/`. Every operation — clone/fetch, push, file edit, merge, branch change — runs directly against R2 through `git-fs.ts`'s `gitFs`; writes run under `withRepositoryLock` and write objects before the refs that name them. Nothing touches local disk.

**No Node-only APIs in app server code**: `src/` uses Web APIs — `fetch`, WebCrypto (`crypto.subtle`, `crypto.getRandomValues`, `crypto.randomUUID`), `TextEncoder`/`TextDecoder`, `atob`/`btoa`, `Uint8Array` — not `node:fs`/`os`/`path`/`crypto`/`https` or `Buffer`; `src/lib/bytes.ts` has the base64/hex/SHA-256 helpers. The one exception is `node:async_hooks` (`perf-log.ts`'s `AsyncLocalStorage`). Operator scripts in `scripts/` may use Node APIs (they run locally, never deploy). Tests may too.

**Database**: Neon (serverless Postgres) via `@neondatabase/serverless`. Schema split: `src/db/schema.ts` (Better Auth tables: user, session, account, verification) and `src/db/app-schema.ts` (app tables: repositories, issues, pullRequests, comments, stars, repositoryCollaborators, activities, tokens, gitAuthAttempts, gitTransactions). ORM: Drizzle. `gitAuthAttempts` isn't app data — it's rate-limit state for `git-auth.ts`'s password-auth path (see above).

**Auth**: Better Auth (`src/lib/auth.ts`). Username and email are immutable after sign-up (`databaseHooks.user.update.before`) — repository storage keys derive from them, so a change would orphan a user's repos and let the next owner of the name inherit them; don't relax this without first moving storage keys to user ids. session accessed server-side via `src/lib/auth-session.ts` → `src/server/session.ts`. `getCurrentUser()` throws on unauthenticated requests; `getCurrentUserOptional()` returns null. Git auth (Basic over HTTPS + PATs) in `src/server/git-auth.ts`. Password reset and email verification send through Resend (`src/lib/email.ts`), wired into Better Auth's `sendResetPassword`/`sendVerificationEmail` hooks. `src/db/schema.ts`'s `user`/`session`/`account`/`verification` tables are hand-maintained, not generated by Better Auth's own migration CLI — a version bump (1.6.22 -> 1.7.2) once added a required `account.issuer` column with no matching schema change, silently breaking every sign-in/sign-up at request time, and 1.7.3 then removed it again, which broke sign-in the opposite way (a required column better-auth never writes) while `pnpm build`/`typecheck`/`test` all stayed green (see `docs/database.md`). Before bumping `better-auth`, diff its actual core schema (`node_modules/@better-auth/core/dist/db/get-tables.mjs`) against `schema.ts`.

**Client data fetching**: All TanStack Query keys and `queryOptions` factories live in `src/lib/query-options.ts` — always source keys from `queryKeys` there instead of inlining strings.

**Server code stays out of the client bundle**: `vite.config.ts` marks `src/db/` and `src/server/` side-effect free for tree-shaking, because server-function files keep their top-level imports in the client build. Don't add a module there that relies on import-time side effects in the browser, and keep server-only SDKs (Sentry's global middlewares in `src/start.ts`) behind server-only dynamic imports. See docs/performance.md#client-bundle-size.

**Heavy client-only dependencies** (`react-markdown`+`remark-gfm`+`rehype-highlight` in `MarkdownRenderer`, Shiki in `CodeViewer`) are `React.lazy`-loaded at every call site, not just imported directly — these routes (tree/repo-home, blob, issue/PR/comment bodies) are hot paths, and eagerly bundling them adds hundreds of KB to a chunk that most visits don't need. Follow the same `lazy(() => import(...))` + `Suspense` pattern for any new heavy, conditionally-rendered client dependency.

**Access control**: `RepositoryAccess` (role: anonymous/read/write/admin/owner, canRead/canWrite/canModerate flags) is computed exclusively in `repo-access.ts` — see above. Call it server-side before any repo mutation.

**Path aliases**: `#/*` and `@/*` both resolve to `src/*`.

## Key Constraints

- `vite.config.ts` sets `ssr.target: "node"` — functions run on Vercel's Node runtime (Fluid compute). Vercel Edge isn't available through this stack: nitro v3 removed the `vercel-edge` preset, and `vercel.functionRules` only re-link the same Node bundle. App code itself is runtime-portable (see "No Node-only APIs" above); what still needs Node is in dependencies — Better Auth's scrypt (`node:crypto`), the Sentry Node SDK, isomorphic-git's global `Buffer`.
- isomorphic-git is used for all git operations — no native git binary dependency anywhere, including tests. The R2 backend (`git-fs.ts`, built on `git-fs-s3`) plugs into its `fs` interface. No operation needs a working directory: commits are built with `git-fs-s3/ops`'s `commitFilesToBare`, merges with `git-edge`'s `threeWayMerge`.
- There is no backwards-compatible legacy storage path handling. `getRepoStorageCoordinates()` returns `{ ownerKey, repoKey }` only — no `legacyOwnerKeys`.
- `nitro` is pinned to an exact beta version (no `^`/`~` range) in `package.json` — deliberate, not a typo; don't loosen it.
- Deployment target is Vercel (`nitro({ preset: "vercel" })` in `vite.config.ts`), not Cloudflare Pages/Workers. Cloudflare is used only for R2 object storage — there's no `@cloudflare/vite-plugin` dependency (it was a dead dependency that got removed; see `docs/security.md`'s "Dependency vulnerabilities"). The app never writes to the function filesystem.
- Biome (not ESLint/Prettier) for lint and format. Config in `biome.json`.
- Add shadcn components via `pnpm dlx shadcn@latest add <component>` — don't hand-write `src/components/ui/*`.
- R2 is reached through `src/lib/r2.ts`'s `createR2ObjectStore` — S3 API requests signed with `aws4fetch` and sent with plain `fetch` (no AWS SDK; Node's fetch pools keep-alive connections itself, and a page load can fire hundreds of R2 reads). `git-fs.ts` owns the one instance; go through `gitFs` or its storage helpers rather than constructing another.
- Repository names are restricted to `/^[a-zA-Z0-9](?:[a-zA-Z0-9._-]*[a-zA-Z0-9])?$/` (`repositories.ts`'s `repoNameSchema`) — this isn't cosmetic, it's the thing that stops a name of `..` or containing `/` from escaping its owner's storage prefix: `gitFs` normalizes `..` in the paths it maps onto R2 keys. `sanitizeStorageSegment` (`git-storage-naming.ts`) re-sanitizes as defense in depth, but don't loosen the input-side regex on the assumption that alone is enough.
- Every branch-name-shaped field anywhere in the app (`files.ts`, `pull-requests.ts`) must be validated with `safeBranchNameSchema`/`isSafeBranchName` (write paths) or `safeRefNameSchema`/`isSafeRefName` (read paths that also accept a pinned commit SHA) from `git-ref-name.ts`, never a bare `z.string()` — `git.commit`/`git.merge`/`git.deleteBranch` don't validate ref names internally the way `git.branch`/`git.writeRef` do, and the R2 backend derives the target repo by parsing the (already `join()`-normalized) path it's given, so an unvalidated branch name is a cross-tenant path traversal reachable from ordinary web-UI actions (branch delete, PR merge), not just a crafted git push. The same applies to any route handler that reads a ref/path straight from request input rather than through one of `files.ts`'s validated `createServerFn`s — see `api/raw.$.ts`, which validates both with `isSafeRefName`/`isSafeRepoPath` before they reach `getFileContent`.
- `MarkdownRenderer`'s link/image renderer is one of the few places rendering fully attacker-controlled content (issue/PR/comment bodies, READMEs) as real `<a href>`/`<img src>` attributes — any change there must keep going through `isSafeHref`/`isSafeImageSrc` (scheme allowlist: relative paths, http(s), mailto; data: images only). Don't reintroduce a raw `<a href={href}>` fallback without that check.
